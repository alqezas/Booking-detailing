## Що покрито

**SQL/інтеграційні (`tests/db`):** рівно 22 товари з точними назвами, обʼємами (зокрема 50 мл ензимної пудри) і цінами; повторний seed без дублів і без перезапису правок; AND між групами фільтрів і OR усередині; набори знаходяться загальними фільтрами; набір не потрапляє в «Креми» через крем у складі; без дублів при many-to-many; фільтр і сортування за ціною набору після знижки; «Новинки» за датою публікації; серверний перерахунок при підміні ціни; −15 %, округлення, без подвійної знижки; історичні ціни й склад набору після редагування; ідемпотентність і відхилення зміненого payload; товар на паузі блокує себе й набори атомарно; підпис checkout LiqPay і відсутність private key у payload; callback з невірним/чужим підписом і зміненим `data`; невірні сума/валюта/order_id; дублікати й статуси не по порядку; reversed → перевірка власницею; повторна оплата з новим `order_id`; паралельні запити не створюють другий платіж; відсутні ключі LiqPay (замовлення зберігається); «зависла» спроба оплати; втрачений callback → `action=status`; прострочення оплати; RLS (анонім, звичайний користувач, адмін), Storage; точка НП іншого міста / неправильного типу, довільний текст замість Ref; недоступність API НП; outbox (конкурентне захоплення, lease, ідемпотентність споживачів, повтори з backoff, dead і повторна обробка).

**Unit (`tests/unit`):** правило округлення знижки, неперетинні цінові діапазони, URL-стан каталогу, валідація телефону й checkout, підпис LiqPay збігається з Node crypto (sha3-256 і sha1), мапінг статусів (`sandbox` лише в sandbox-режимі), кошик (обмеження, пошкоджений localStorage).

**Playwright (`tests/e2e`, з тестовими адаптерами):**
1. Каталог → фільтр (назад/вперед браузера) → товар → кошик → дані покупця → населений пункт → відділення → оформлення → оплата на сторінці адаптера → статус із сервера «Оплату підтверджено LiqPay» → замовлення в адмінці зі складом і доставкою.
2. Набір на fixtures: фільтр «Зволоження та живлення» → склад, «Окремо» 1 600 грн, −15 %, 1 360 грн → кошик з окремим тоніком (економія −240, разом 1 760) → поштомат → оплата → у власниці склад набору для комплектації.
3. Підроблена ціна в localStorage → сервер показує справжню.
4. Офлайн: кошик зберігається й редагується, оформлення й оплата заблоковані, запитів до функцій немає.
5. Телефон: без горизонтального скролу на 6 сторінках, картки вирівняні, мобільна панель фільтрів.

E2E знайшли й допомогли виправити реальну помилку: сторінка замовлення в адмінці не відкривалась (неоднозначний звʼязок `orders` ↔ `payment_attempts`).

## Перевірка з реальними API

- **Нова пошта:** `searchSettlements` і `getWarehouses` (`TypeOfWarehouseRef`, `FindByString`, пагінація) перевірено ручними запитами до api.novaposhta.ua. Автотесту проти живого API немає.
- **LiqPay:** формат за актуальною документацією (підпис `base64(sha3-256(private_key + data + private_key))`, callback `data`+`signature`, `action=status`), але **зі справжніми ключами не перевірявся**. Усі платіжні тести — через контрольований адаптер `tests/fakes/liqpay.ts`; це не перевірка зовнішньої інтеграції.
- Хмарний Supabase, деплой Vercel, cron через Vault — **не виконувались** (немає доступу).

## Обмеження

- shadcn/ui не підключено (правило AGENTS.md без Tailwind; документація Astryx радить заміну на компоненти Astryx). Шторка — Astryx `BottomSheet`.
- SEO: prerender лише `<head>` (метадані, canonical, structured data); тіло сторінки рендериться в браузері.
- Вбудований браузер десктопного застосунку блокує запити service worker до локального Supabase; у Chromium (Playwright) і з хмарним Supabase працює. Для налагодження: `localStorage['gt-no-sw']='1'`.
